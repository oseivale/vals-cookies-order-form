# Sweet Batch Cookie Co. — Order App (Next.js 16 build)

A Next.js (App Router + TypeScript + Tailwind) ordering form for a weekly
cookie business: customers build one or more cookie-pack orders with mixed
flavours, pay by Stripe or Interac e-Transfer, and get a branded confirmation
email once payment is confirmed. Orders are capped at a total number of
cookies per week (resets Mondays, America/Toronto time).

**This is the Next.js `16.3.5` copy of the project**, kept as a separate
folder from the Next.js `14.x` build rather than an upgrade in place, so you
can try the newer version without disturbing anything already running. It
has the exact same features, database schema, and **identical environment
variable names** as the 14.x build — copy your existing `.env` values over
as-is, nothing needs renaming. See [`STRIPE_TESTING.md`](./STRIPE_TESTING.md)
for a full walkthrough of testing a real purchase end-to-end.

## What's different from the Next.js 14 build

Next.js 16 made a few breaking changes that this copy already accounts for,
so you shouldn't need to do anything extra — this section is just so you
know what changed under the hood:

- **`cookies()` is now async everywhere.** `app/admin/page.tsx` now does
  `const cookieStore = await cookies();` — synchronous access was removed
  entirely in v16 (it was still a working (deprecated) shortcut in v15).
- **Dynamic route `params` are now a `Promise`.** Every route with a
  `[id]` segment (`app/order/[id]/confirmation/page.tsx`,
  `app/api/orders/[id]/route.ts`,
  `app/api/admin/orders/[id]/confirm/route.ts`,
  `app/api/admin/orders/[id]/cancel/route.ts`) now does
  `const { id } = await params;` instead of reading `params.id` directly.
- **Turbopack is the default bundler** for both `next dev` and
  `next build` — no `--turbopack` flag needed, and there's nothing to
  opt out of since this app has no custom webpack config.
- **`next lint` was removed.** `npm run lint` now runs the plain ESLint
  CLI (`eslint .`) against a flat-config file (`eslint.config.mjs`)
  instead of the old `.eslintrc.json`.
- **Node.js 20.9+ and TypeScript 5.1+ are now required minimums** (up
  from Node 18.18+) — check `node -v` before you `npm install`.
- **React 19.2** ships with Next 16's App Router; `package.json` here
  pins `react`/`react-dom` to `19.2.0` accordingly.
- The one thing that **didn't** need to change:
  `NextRequest.cookies.get(...)` inside `lib/auth.ts`'s `isAdminRequest` —
  that's a different, still-synchronous API attached directly to the
  request object in Route Handlers, unrelated to the `next/headers`
  `cookies()` function above.

> **A note on how this was built:** every file in this project was
> hand-written rather than generated by `create-next-app`/`npm install`,
> because this build environment's network policy blocks
> `registry.npmjs.org` (a 403 even though it's normally reachable) — so no
> npm install could be run or verified here. That means **the very first
> `npm install` and `npm run build` for this project need to happen on your
> machine or on Netlify**, not here. Everything below assumes that first
> install hasn't happened yet.

## 1. What's included

- Three pack sizes (Two of a Kind / Six Picks / Friends Dozen), three
  flavours, mix-and-match within a pack, "add another box" for multiple
  packs in one order.
- Live weekly cookie cap (default 200/week, resets Monday
  America/Toronto), enforced server-side with a Postgres advisory lock so
  concurrent orders can't oversell it.
- Stripe Checkout (card) or Interac e-Transfer (manual confirmation) at
  checkout.
- Nodemailer (via Resend's SMTP relay) sends a branded confirmation email
  the moment an order is actually paid — a Stripe webhook for card
  payments, or an admin clicking "Mark paid" for e-Transfers.
- Choosing e-Transfer also fires a **second, immediate email** with the
  send-to address, amount, and reference code, confirming the order is
  reserved but pending until payment arrives — in addition to (not instead
  of) redirecting the customer to the confirmation page showing the same
  details.
- A tiny password-protected `/admin` dashboard to see orders and confirm/
  cancel pending e-Transfers.
- Branded in your colors (`#fa945d` / `#eac394` / `#996236`) with a
  hand-drawn cookie logo (`public/logo.svg`) in the welcome header and
  confirmation page.

## 2. Set up your accounts

You'll need, all free to start:

1. **A Postgres database.** [Neon](https://neon.tech) has a free tier and
   works well with serverless functions. Create a project, copy the
   connection string.
2. **A Stripe account.** [dashboard.stripe.com](https://dashboard.stripe.com) →
   Developers → API keys, for `STRIPE_SECRET_KEY`. You'll add the webhook
   secret after your first deploy (step 5).
3. **A Resend account** (for sending email via Nodemailer).
   [resend.com](https://resend.com) → API Keys, and verify a sending domain
   under Domains so `FROM_EMAIL` can use your own domain.
4. **A Netlify account**, with the [Netlify CLI](https://docs.netlify.com/cli/get-started/)
   installed (`npm install -g netlify-cli`) if you want to deploy from your
   terminal instead of connecting a Git repo.

## 3. Local setup

```bash
npm install          # first real install — this project was hand-authored, not scaffolded
cp .env.example .env # then fill in every value
npm run db:init       # creates the orders table using DATABASE_URL from .env
npm run dev            # http://localhost:3000
```

> **Already had this project running before tax support was added?** `npm run db:init` only creates tables that don't exist yet — it won't add new columns to a table you already created. Run `migrations/001_add_tax_columns.sql` once against your database first (Neon's SQL editor, or `psql "$DATABASE_URL" -f migrations/001_add_tax_columns.sql`), then `npm run db:init` and `npm run dev` as usual.

For Stripe webhooks in local dev, use the Stripe CLI:

```bash
stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

It will print a `whsec_...` value — put that in your local `.env` as
`STRIPE_WEBHOOK_SECRET` while testing locally.

**To actually run a full test purchase (card and e-Transfer) and confirm
every email fires**, see [`STRIPE_TESTING.md`](./STRIPE_TESTING.md) — it
covers test-mode API keys, test card numbers, and a step-by-step walkthrough
of both payment paths.

## 4. Deploy to Netlify

1. Push this project to a GitHub/GitLab/Bitbucket repo (or use
   `netlify deploy` from the CLI directly).
2. In Netlify: **Add new site → Import an existing project**, pick the
   repo. Build command and publish directory are already set in
   `netlify.toml` (`npm run build` / `.next`), and the
   `@netlify/plugin-nextjs` plugin is declared there too — Netlify will
   install it automatically.
3. Under **Site settings → Environment variables**, add every variable from
   `.env.example` with your real values. Set `SITE_URL` to your Netlify
   URL (e.g. `https://your-site.netlify.app`, or your custom domain once
   attached).
4. Deploy. Once it's live, run `npm run db:init` once against your
   production `DATABASE_URL` (from your machine, with `.env` pointed at
   prod) to create the `orders` table — or just run the contents of
   `schema.sql` directly in Neon's SQL editor.
5. **Set up the Stripe webhook against your live URL:**
   [dashboard.stripe.com/webhooks](https://dashboard.stripe.com/webhooks) →
   Add endpoint → URL = `https://your-site.netlify.app/api/webhooks/stripe`
   → select events `checkout.session.completed` and
   `checkout.session.expired` → save, then copy the new **Signing secret**
   into Netlify's `STRIPE_WEBHOOK_SECRET` env var and redeploy (env var
   changes need a redeploy to take effect).

## 5. Customizing

- **Tax** is a flat rate applied to every order's subtotal, set in
  `lib/config.ts` (`TAX_RATE` / `TAX_LABEL`) — defaults to 13% Ontario HST.
  It's computed once server-side per order and stored on the order itself
  (`subtotal_cents` / `tax_cents` / `total_cents`), so a future rate change
  never rewrites past orders. Shows up consistently in the order form,
  Stripe Checkout (as its own line item), e-Transfer instructions, the
  confirmation email, and the admin dashboard.
- **Packs, flavours, prices, the weekly cap, and brand colors** all live in
  one place: `lib/config.ts`. Change numbers there and the whole app (form,
  emails, admin dashboard) picks them up.
- **Logo:** swap `public/logo.svg` for your own artwork any time — same
  path, same spot in `app/page.tsx` and
  `app/order/[id]/confirmation/page.tsx`.
- **Confirmation email copy:** `lib/email.ts`.
- **Admin password:** `ADMIN_PASSWORD` env var — it's a single shared
  password, not a full user system, which is enough for one admin dashboard.

## 6. How the weekly cap actually works

Cookies count against the current week's cap the moment an order is
created — not only once it's paid — so two customers can't both be shown
"cookies available" for the last few boxes and then both pay. Specifically,
an order counts if it's `paid`, or `pending_etransfer` (it's reserved until
an admin confirms or cancels it), or `pending_stripe` and less than 30
minutes old (a Stripe Checkout session someone actually has open right
now). Abandoned card checkouts older than 30 minutes are automatically
excluded and release their reserved cookies. All of this is computed inside
a Postgres transaction holding a per-week advisory lock
(`lib/db.ts` → `withWeeklyCapLock`), so concurrent submissions for the same
week are serialized against each other and can't both slip through.

## 7. Project structure

```
app/
  page.tsx                     welcome + order form (home page)
  layout.tsx, globals.css      fonts, brand CSS
  order/[id]/confirmation/     post-order status page (paid / awaiting e-Transfer / processing)
  admin/                       password-gated dashboard
  api/
    cap-status/                GET current weekly cap status
    orders/                    POST create an order; GET /:id status
    webhooks/stripe/           Stripe webhook (marks orders paid, sends email)
    admin/                     login, order list, confirm/cancel e-Transfers
components/
  OrderForm.tsx                the whole multi-pack builder UI
  ConfirmationView.tsx         post-order status UI (polls while Stripe finalizes)
  AdminDashboard.tsx           order list + confirm/cancel buttons
lib/
  config.ts                    packs, flavours, prices, cap, brand colors — the source of truth
  order.ts                     shared types + zod validation + total helpers
  cap.ts                       weekly window + race-safe cap checking
  db.ts                        Postgres pool + all queries
  stripe.ts, email.ts, auth.ts Stripe client, Nodemailer/Resend, admin sessions
schema.sql                     run once to create the orders table
scripts/init-db.js             `npm run db:init` convenience wrapper around schema.sql
netlify.toml                   Netlify build + Next.js plugin config
```

## 8. Known limitations / next steps

- Admin auth is a single shared password — fine for one person, not a
  multi-user system.
- There's no automated test suite. Given this was built without local
  `npm install` access, **run `npm run build` yourself before your first
  deploy** to catch any typos before Netlify does.
- e-Transfer confirmation is manual by design (Interac has no public
  verification API for small businesses) — budget a few minutes a day to
  check your e-Transfer inbox against `/admin`.
